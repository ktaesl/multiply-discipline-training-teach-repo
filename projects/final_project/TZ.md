# Техническое задание на итоговый проект

**Дисциплина:** Информационные технологии **Курс:** 2 курс, специальность «Информационные технологии» **Учебный год:** 2026–2027 **Тема проекта:** «Информационная система кафе: сайт для покупателей и внутренняя CRM для сотрудников» **Вид работы:** индивидуальный итоговый проект

## 1. Общие сведения

Проект является продолжением сквозной работы, которую студенты выполняли на занятиях и в домашних заданиях: консольной программы кафе (меню в словаре `menu`, заказ в словаре `order`, подсчёт суммы, скидка, чек). В итоговом проекте эта логика переносится в веб-приложение с базой данных.

Проект состоит из двух частей:

1. **Публичный сайт** для покупателей: просмотр меню, корзина, оформление заказа.
2. **Внутренняя CRM** для сотрудников: вход по логину и паролю, работа с заказами, клиентами и меню.

## 2. Цель и задачи

**Цель:** закрепить навыки программирования на Python и научиться создавать простое веб-приложение с базой данных, которое решает практическую задачу бизнеса.

**Задачи:**

- спроектировать структуру сайта и CRM;
- сверстать страницы на HTML и CSS;
- реализовать серверную логику на Python;
- подключить базу данных PostgreSQL (совместно с преподавателем);
- реализовать разграничение доступа (покупатель / сотрудник);
- оформить проект в репозитории и подготовить защиту.

## 3. Распределение ответственности

| Часть проекта | Кто выполняет |
| --- | --- |
| Вёрстка страниц (HTML, CSS) | студент **самостоятельно** |
| Серверная логика на Python (маршруты, обработка форм, бизнес-логика) | студент **самостоятельно** |
| Проектирование и создание БД PostgreSQL, подключение к ней | студент **вместе с преподавателем** |
| Отладка, тестирование, оформление, защита | студент |

Преподаватель предоставляет заготовку схемы БД (`schema.sql`), помогает установить PostgreSQL и настроить подключение, объясняет SQL-запросы. Студент должен понимать каждый запрос в своём проекте и уметь его объяснить.

## 4. Технические требования

### 4.1. Стек

- **Язык:** Python 3.10 и выше.
- **Веб-фреймворк:** Flask (простой фреймворк с шаблонизатором Jinja2). Использование другого фреймворка согласуется с преподавателем.
- **Шаблоны:** HTML-файлы в папке `templates/`, стили в `static/css/`.
- **Стили:** чистый CSS, без Bootstrap и других CSS-фреймворков. JavaScript не обязателен.
- **СУБД:** PostgreSQL, библиотека `psycopg2` (допустимо `psycopg2-binary`), SQL-запросы пишутся вручную.
- **Пароли:** хранятся только в виде хэша (`werkzeug.security`).
- **Версионирование:** Git, репозиторий на GitHub.

## 5. Функциональные требования

### 5.1. Публичный сайт (для покупателей)

Авторизация покупателя не требуется.

**Обязательные страницы и функции:**

1. **Главная страница**: название кафе, краткое описание, контакты, ссылка на меню.
2. **Меню**:
   - список позиций, сгруппированных по категориям;
   - у позиции: название, описание, цена;
   - кнопка «Добавить в корзину».
3. **Корзина**:
   - список выбранных позиций с количеством (логика словаря `order`: «название → количество»);
   - возможность увеличить, уменьшить количество и удалить позицию;
   - стоимость каждой позиции и общая сумма;
   - скидка по правилу, которое студент берёт из домашнего задания (например, 10% при сумме заказа от заданного порога);
   - сообщение, если корзина пуста.
4. **Оформление заказа**: форма с полями «имя», «телефон», «комментарий». Обязательна проверка заполнения полей на сервере.
5. **Страница «Заказ оформлен»**: номер заказа, состав, итоговая сумма (чек).
6. **Страница ошибки 404** с понятным текстом.

**Дополнительно (на оценку выше):** поиск по меню, фильтр по категории, страница «Мои заказы» по номеру телефона, адаптивная вёрстка.

### 5.2. Внутренняя CRM (для сотрудников)

Доступна только после входа. Неавторизованного пользователя при попытке открыть страницу CRM необходимо перенаправлять на страницу входа.

**Роли:**

| Роль | Возможности |
| --- | --- |
| Сотрудник (`staff`) | просмотр заказов, смена статуса заказа, просмотр клиентов |
| Администратор (`admin`) | всё, что доступно сотруднику, плюс управление меню и сотрудниками |

**Обязательные страницы и функции:**

1. **Вход / выход**: логин и пароль, сообщение при неверных данных, выход из системы.
2. **Список заказов**:
   - таблица: номер, дата и время, имя клиента, сумма, статус;
   - фильтр по статусу;
   - сортировка: новые заказы сверху.
3. **Карточка заказа**: данные клиента, состав заказа (позиция, количество, цена, сумма), скидка, итог, кнопка смены статуса. Статусы: `новый` → `готовится` → `готов` → `выдан`; также возможен `отменён`.
4. **Клиенты**: список клиентов (имя, телефон), количество заказов и общая сумма заказов клиента.
5. **Управление меню** (только администратор): добавление, редактирование, удаление (или скрытие) позиции, изменение цены и категории.
6. **Простая статистика** на главной странице CRM: количество новых заказов, количество заказов за сегодня, выручка за сегодня.

**Дополнительно:** управление сотрудниками (добавление, блокировка), поиск заказа по номеру или телефону, выгрузка заказов за день в `.csv`.

## 6. Требования к базе данных

База данных проектируется и создаётся совместно с преподавателем. Минимальный набор таблиц (названия и состав уточняются при проектировании):

| Таблица | Назначение | Основные поля |
| --- | --- | --- |
| `categories` | категории меню | `id`, `name` |
| `menu_items` | позиции меню | `id`, `category_id`, `name`, `description`, `price`, `is_active` |
| `customers` | клиенты | `id`, `name`, `phone` |
| `orders` | заказы | `id`, `customer_id`, `created_at`, `status`, `comment`, `discount`, `total` |
| `order_items` | состав заказа | `id`, `order_id`, `menu_item_id`, `quantity`, `price` |
| `employees` | сотрудники | `id`, `login`, `password_hash`, `full_name`, `role` |

**Требования:**

- у каждой таблицы есть первичный ключ;
- связи между таблицами реализованы внешними ключами;
- на цену и количество наложены ограничения (значение больше нуля);
- в `seed.sql` лежат тестовые данные: не менее 3 категорий, 10 позиций меню, 5 клиентов, 8 заказов, 2 сотрудников (администратор и сотрудник);
- запросы выполняются параметризованно (`cursor.execute(sql, params)`), без подстановки значений в строку SQL (защита от SQL-инъекций);
- цена позиции фиксируется в `order_items.price` в момент заказа, чтобы изменение меню не меняло старые заказы.

В ходе работы студент должен самостоятельно написать запросы: `SELECT` с `JOIN`, `INSERT`, `UPDATE`, `DELETE`, а также `GROUP BY` для статистики.

## 7. Нефункциональные требования

- код читаемый: понятные имена переменных и функций, логика разбита на функции, есть комментарии к ключевым местам;
- подключение к БД вынесено в отдельный модуль `db.py`, пароль к БД не хранится в публичном репозитории (используется переменная окружения или отдельный файл настроек, добавленный в `.gitignore`);
- сайт открывается и работает без ошибок в современных браузерах;
- единый стиль оформления страниц сайта и отдельный стиль для CRM;
- все ошибки ввода обрабатываются: пользователь видит понятное сообщение, а не трассировку Python;
- проект запускается по инструкции из `README.md` на другом компьютере.

## 8. Этапы выполнения

Сроки и количество занятий на каждый этап уточняет преподаватель. Ниже указана рекомендуемая последовательность.

| № | Этап | Результат | Кто |
| --- | --- | --- | --- |
| 1 | Подготовка | создана папка проекта в `projects/`, согласована тема, составлен список страниц | студент |
| 2 | Вёрстка | статические HTML-страницы сайта и CRM, файлы CSS | студент самостоятельно |
| 3 | Flask без БД | маршруты, шаблоны Jinja2, меню и корзина на словарях Python (как в домашнем задании 2) | студент самостоятельно |
| 4 | База данных | схема БД, `schema.sql`, `seed.sql`, подключение через `db.py` | студент вместе с преподавателем |
| 5 | Перенос на БД | меню, заказы и клиенты читаются и сохраняются в PostgreSQL | студент с консультацией преподавателя |
| 6 | CRM | вход, роли, список и карточка заказа, смена статуса, управление меню | студент |
| 7 | Тестирование и оформление | проверка по чек-листу, `README.md`, скриншоты | студент |
| 8 | Защита | демонстрация проекта и ответы на вопросы | студент |

**Контрольные точки.** Преподаватель проверяет проект после этапов 3, 5 и 6. Статус каждой работы указывается в `README.md` папки проекта таблицей:

| файл | статус |
| --- | --- |
| app.py | в работе |

Выполнение этапов допускается с задержкой не более 7 дней после дедлайна (правило репозитория дисциплины).

## 11. Порядок защиты

Длительность: 7–10 минут на студента.

1. Краткий рассказ о проекте (1–2 минуты).
2. Демонстрация сценария: покупатель выбирает позиции → оформляет заказ → сотрудник входит в CRM → находит заказ → меняет статус.
3. Показ структуры БД и одного-двух запросов из кода.
4. Ответы на вопросы преподавателя.

**Примеры вопросов:**

- Чем словарь `order` в корзине отличается от таблицы `order_items` в БД?
- Зачем в `order_items` хранится цена, если она есть в `menu_items`?
- Почему нельзя хранить пароль сотрудника в открытом виде?
- Что такое внешний ключ и какие есть в вашей БД?
- Что произойдёт, если неавторизованный пользователь откроет страницу CRM?
- Что делает `JOIN` в запросе карточки заказа?
